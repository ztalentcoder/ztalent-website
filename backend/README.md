# Backend deployment notes

## Initial SUPER_ADMIN provisioning

The backend does not create administrator accounts during startup and has no
public registration endpoint. To provision the first administrator, use a
trusted interactive terminal connected to the intended database:

```powershell
cd C:\path\to\ztalent-coder\backend
npm run admin:provision
```

The command prompts for a name and email, then requests the password twice
without echoing it to the terminal. Use a unique password of at least 12
characters; it is hashed with the existing Argon2id utility. Email addresses
are trimmed and lowercased using the same validation as admin login. The
command creates a `SUPER_ADMIN` only if no admin account exists, inside a
serializable transaction. It refuses to modify or replace an existing account.
The password is never accepted as a command-line argument, environment
variable, or printed output.

On Windows PowerShell, run the command in an interactive console, not through
a pipeline or background job. For deployment, run it once from an approved,
access-controlled operations host or one-off management container with a
terminal attached and the production `DATABASE_URL` supplied through the
deployment's existing secret-management mechanism. Confirm the target database
before entering account details. Do not copy production credentials into
shell history or commit them to `.env` or source control. The provisioning
command is deliberately separate from normal application startup.

## Managed CMS image uploads

Admin CMS images are stored on the backend filesystem under
`backend/uploads/images/` and served from `/uploads/images/`. The backend
creates these resource folders as needed:

- `company/`
- `business-areas/`
- `projects/`
- `blog/`
- `team/`

Uploads require an authenticated `SUPER_ADMIN` or `EDITOR` session. The API
accepts one JPEG, PNG, or WebP file (maximum 5 MB) as the `image` field in
`multipart/form-data`:

- `POST /api/admin/images/{company-profile,business-areas,projects,blog-posts,team-members}`
- `DELETE /api/admin/images` with JSON body `{ "url": "<image URL>" }`

Uploaded file content is decoded and re-encoded before it is written. Filenames
are generated by the backend and never use the client-provided filename. The
database continues to use its existing nullable image URL fields; new local
images are stored as paths such as `/uploads/images/projects/<generated-id>.webp`.
Existing externally hosted URLs remain valid and no database migration is
required. Replaced images are deleted only after the new upload and CMS save
succeed. Deletion ignores external paths and skips local images still referenced
by any CMS record.

Local filesystem storage is intended for development. In production, the host
must provide persistent storage mounted at the backend's `uploads` directory
(or configure durable storage at the platform level). Do not rely on an
ephemeral container filesystem: uploaded files may be lost when an instance is
restarted or redeployed. The `uploads/images` directory is excluded from source
control and should be backed up according to the deployment's data-retention
requirements.

## Contact endpoint rate limiting

`POST /api/contact` uses an in-memory limit of five requests per client IP per
15 minutes and returns standard `RateLimit` headers. The in-memory store is
appropriate only for a single backend instance; deployments with multiple
instances must configure a shared `express-rate-limit` store to enforce one
consistent limit across instances.

The application does not enable Express `trust proxy`. Behind a reverse proxy,
configure Express to trust only the actual proxy or proxy network used by the
deployment before relying on forwarded client IP addresses. Do not trust
arbitrary `X-Forwarded-For` values or enable unrestricted proxy trust.

## Admin CMS API

Admin CMS routes require a valid admin session. Content routes permit
`SUPER_ADMIN` and `EDITOR`; contact-message list, detail, and status routes are
restricted to `SUPER_ADMIN`.

- `GET /api/admin/dashboard`
- `GET`, `PUT`, `PATCH /api/admin/company-profile`
- `GET`, `POST /api/admin/company-profile/social-links`
- `GET`, `PUT`, `PATCH`, `DELETE /api/admin/company-profile/social-links/:id`
- `GET`, `POST /api/admin/{business-areas,services,projects,academic-courses,blog-categories,blog-posts,team-members,testimonials,site-statistics}`
- `GET`, `PUT`, `PATCH`, `DELETE /api/admin/{resource}/:id` for each resource above
- `GET /api/admin/contact-messages` (supports `page`, `pageSize`, `search`,
  `status`, and `topic`)
- `GET /api/admin/contact-messages/:id`
- `PATCH /api/admin/contact-messages/:id` (status only; no delete route)

Collection responses are `{ status: "success", items, pagination }`, where
`pagination` contains `page`, `pageSize`, `total`, and `pageCount`. Single-item
and write responses use `{ status: "success", item }`; deletes return
`{ status: "success" }`. Dashboard counts use `businessAreas`, `services`,
`projects`, `blogPosts`, `teamMembers`, and `newContactMessages`.

## Public CMS content API

The public content API is read-only and does not require an admin session.
Content models with publication status are filtered to `PUBLISHED`. Public
responses use explicit field selections and serializers; company contact fields
and active social links are provided for the public website.

- `GET /api/public/company-profile`
- `GET /api/public/statistics` (live counts of published courses, projects,
  services in published business areas, and blog articles; not cached)
- `GET /api/public/business-areas` and `/api/public/business-areas/:slug`
- `GET /api/public/services` (optional `businessArea` slug filter)
- `GET /api/public/projects` (optional `businessArea` slug filter) and
  `/api/public/projects/:slug`
- `GET /api/public/academic-courses` (optional `level` filter) and
  `/api/public/academic-courses/:slug`
- `GET /api/public/blog-categories` (only categories with published posts)
- `GET /api/public/blog-posts` (optional `category` slug filter) and
  `/api/public/blog-posts/:slug`
- `GET /api/public/team-members`
- `GET /api/public/testimonials`
- `GET /api/public/site-statistics` (active statistics only)

Content collections accept `page` and `pageSize` (maximum 50) and return the standard
`{ status: "success", items, pagination }` response. Detail responses use
`{ status: "success", item }`. Missing and unpublished slugs share a generic
404 response. The statistics endpoint returns four numeric counts with
singular/plural labels and does not use manually managed SiteStatistic entries.
Contact messages and administrative models are not exposed.
